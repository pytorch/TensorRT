# BEVFormer camera-to-output figure

This workflow produces six camera images with projected detection boxes and a
bird's-eye-view detection plot. It uses actual saved outputs, not drawn example
detections. The renderer runs offline; it adds no Python dependency to the
native DRIVE application.

## Current status

The recorded-input preparation and rendering code has CPU tests. nuScenes mini
and the CAN-bus expansion have been downloaded locally; the first three
keyframes of scene-0061 are selected. A fresh native run is still required
before a figure can be described as a real-scene DRIVE result. October evidence used
synthetic inputs. No real-camera result has been inserted into the blog.

## Required assets

- A local nuScenes mini or validation scene with all six original 1600×900
  camera images. Use data whose terms permit the intended publication.
- The nuScenes JSON metadata and CAN-bus expansion. The direct reader below
  uses the supplied calibration and poses, and rejects missing CAN-bus data.
  Alternatively, use trusted temporal infos generated by the upstream converter.
- The existing official BEVFormer-Tiny checkpoint and matching model adapter.
- The already-exported mixed `.pte` / `.ptd` bundle and `validate_pte` binary
  built for the target's TensorRT/CUDA stack.

All paths below are supplied by the caller. `DEMO_SRC` is this directory,
`MODEL_SRC` contains the maintained BEVFormer `model.py` and `attention.py`,
and `WORK` is a new output directory. In this checkout, `MODEL_SRC` can equal
`DEMO_SRC`: both refer to `examples/torchtrt_executorch_example/bevformer/`.
Keep datasets and generated outputs outside the source checkout.

## Download the dataset

The [official tutorial](https://www.nuscenes.org/tutorials/nuscenes_tutorial.html)
publishes the mini archive. CAN-bus is available through the
[Motional public distribution](https://registry.opendata.aws/motional-nuscenes/).
Mini is about 4.17 GB compressed; CAN-bus is about 0.78 GB. Allow additional
space for extraction and generated tensors. Set `DOWNLOADS` and `NUSCENES_ROOT`
to local data directories before running:

```bash
mkdir -p "$DOWNLOADS" "$NUSCENES_ROOT"
curl -fL --retry 3 -o "$DOWNLOADS/v1.0-mini.tgz" \
  https://www.nuscenes.org/data/v1.0-mini.tgz
curl -fL --retry 3 -o "$DOWNLOADS/can_bus.zip" \
  https://d36yt3mvayqw5m.cloudfront.net/public/v1.0/can_bus.zip
```

SHA-256 values of the archives retrieved on November 10, 2026:

```text
943037abbb3b26b3070dc76504a43eb440503b00baf9ac2f1538d9c03fc9298f  v1.0-mini.tgz
3c68b94c001e8bd05a19886ecb2c6854e0cd69d7005ed9a94d13d45d2951e83f  can_bus.zip
```

Save those lines as `SHA256SUMS` in `DOWNLOADS`, then verify and extract:

```bash
(cd "$DOWNLOADS" && sha256sum -c SHA256SUMS)
tar -xzf "$DOWNLOADS/v1.0-mini.tgz" -C "$NUSCENES_ROOT"
unzip "$DOWNLOADS/can_bus.zip" -d "$NUSCENES_ROOT"
```

The root now contains `samples/`, `sweeps/`, `maps/`, `v1.0-mini/` and
`can_bus/`. Data and pretrained weights are not included in Git.

## 1. Select recorded frames

Use the beginning of a scene so the previous-BEV state starts at zero. The
converter selects consecutive keyframes and preserves the expected camera order.
No nuScenes SDK or old training framework is needed for the direct JSON reader:

```bash
mkdir -p "$WORK"
python "$DEMO_SRC/manifest_from_nuscenes.py" \
  --data-root "$NUSCENES_ROOT" --version v1.0-mini \
  --scene scene-0061 --frames 3 --output "$WORK/scene.json"
```

The reader accounts for camera and LiDAR capture-time poses. It preserves the
pinned upstream CAN-bus timestamp convention: position/orientation use the last
preceding message (or the first available message); other fields use the loop's
final message, the first later message when present. The dataset layer then
replaces position/orientation with the keyframe ego pose.

For existing temporal infos, this alternative creates the same manifest format.
Only load pickle files from a trusted source: Python pickle can execute code.

```bash
python "$DEMO_SRC/manifest_from_infos.py" \
  --infos "$INFOS" --trust-info-pickle \
  --data-root "$NUSCENES_ROOT" --scene-token "$SCENE_TOKEN" \
  --frames 3 --output "$WORK/scene.json"
```

Alternatively provide the JSON manifest directly. It has `schema` set to
`bevformer-recorded-v1`, `input_kind` set to `recorded`, and a `frames` list.
Each frame requires `sample_token`, `scene_token`, `prev_token`, `timestamp_us`,
`ego_translation` (global XYZ), `ego_rotation_wxyz`, the full 18-value `can_bus`,
and a `cameras` dictionary. Its six keys are `CAM_FRONT`, `CAM_FRONT_RIGHT`,
`CAM_FRONT_LEFT`, `CAM_BACK`, `CAM_BACK_LEFT`, `CAM_BACK_RIGHT`; each contains
an `image` path and a 4×4 `lidar2img` matrix for the ORIGINAL image, from the
current keyframe LiDAR coordinate system. Do not substitute arbitrary photographs
or identity calibration. Camera timestamps need not be identical; upstream
extrinsics account for capture-time ego poses.

## 2. Prepare model inputs and PyTorch references

```bash
python "$DEMO_SRC/prepare_recorded.py" \
  --manifest "$WORK/scene.json" --source-dir "$MODEL_SRC" \
  --checkpoint "$CHECKPOINT" --output-dir "$WORK/cases"
```

The preprocessing matches the Tiny test configuration: RGB normalization with
the checkpoint's mean/std, OpenCV half-scale resize, then zero padding to
480×800. Projection matrices are scaled with the images. It does not resize
450 rows directly into 480 rows, which would distort the projection.

The full motion vector is retained. Global position becomes frame-to-frame
translation; the last yaw entry becomes the degree delta; the penultimate
entry remains absolute yaw in radians. The original upstream yaw subtraction
is preserved even across the 0/360 boundary. A scene reset clears history.
Preparation carries the PyTorch BEV state; the native runner carries its OWN
state. This is intentionally a correctness workflow, not a timing benchmark.

## 3. Run the native application

Transfer/share the cases directory with the target. Original camera JPEGs are
only needed later for rendering, not by the native application.

```bash
"$VALIDATOR" --model="$BUNDLE/model.pte" \
  --data="$BUNDLE/aoti_cuda_blob.ptd" \
  --bev-sequence="$CASES_ON_DRIVE/sequence.txt" \
  --output="$NATIVE_RESULTS"
```

Keep the existing 3e-4 absolute/relative tolerances. The runner saves each
frame's actual outputs and comparison report. A mismatch must be investigated
before presenting the native result; the new input path has not established
that arbitrary real-camera inputs meet those tolerances.

## 4. Render the result

Bring the native output directory back to the environment containing the
original images and prepared cases. Camera paths in `frame.json` refer to that
environment. Frame 2 uses history from frames 0 and 1.

```bash
python "$DEMO_SRC/render_recorded.py" \
  --case-dir "$WORK/cases/frame_002" \
  --raw-output-dir "$NATIVE_RESULTS/frame_2" --source native \
  --score-threshold 0.3 --output "$WORK/bevformer-native.png"
```

For an explicitly labeled PyTorch preview, use the same case directory for both
paths and `--source pytorch`. That is not a native DRIVE result.

The plot uses original camera calibration, near-plane clipping, LiDAR-frame
metric axes and oriented boxes. The display threshold is recorded, not an
accuracy metric. Detections are predictions, not ground truth. The JSON sidecar
records sample identity, image/output hashes, output comparisons and threshold.
The image provenance is checked before rendering; no different road image can
silently replace the actual inference input. Synthetic test inputs receive a
prominent synthetic label and must not be used as blog inference evidence.
